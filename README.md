# Textdrop

Личная лента для обмена текстом и файлами между устройствами: один пароль, SQLite, поиск и корзина. Python 3.12+; Pillow используется только для подготовки миниатюр в отдельном процессе. Адрес: `https://share.nikitalebe.dev`.

## Запуск с существующим Caddy в Docker

Выполняйте команды в обычной SSH-сессии с доступом к Docker. Нужен Docker Compose v2+. Текущий контейнер Caddy — `caddy-caddy-1`, сеть — `caddy_default`. Проверить их можно так:

```bash
docker ps --format 'table {{.Names}}\t{{.Networks}}'
docker network inspect caddy_default --format '{{.Driver}}'
```

Используйте пользовательскую bridge-сеть Caddy, поддерживающую DNS контейнеров. Если Caddy использует `host` или стандартную сеть `bridge`, потребуется отдельная общая сеть и её подключение в конфигурации Compose Caddy.

```bash
cd ~/textdrop
python3 deploy/setup-docker-secrets.py
python3 deploy/setup-docker-secrets.py --check
docker compose up -d --build
docker compose ps
```

По умолчанию используется сеть `caddy_default`; для другой сети задайте `CADDY_NETWORK`. Скрипт спрашивает пароль интерактивно и не перезаписывает секреты. Повторный запуск создаёт только недостающие файлы, в том числе после прерванной настройки. Проверка `--check` не создаёт и не меняет секреты. Приложение работает без root, хранит SQLite в именованном томе и не публикует порт 8765 на хосте. Caddy обращается к нему по имени `textdrop-share` в общей сети.

Чтобы найти действующий Caddyfile на хосте, посмотрите bind mounts:

```bash
docker inspect caddy-caddy-1 --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
```

Если `/etc/caddy` смонтирован как каталог, файл находится в его источнике под именем `Caddyfile`. Сделайте резервную копию файла перед изменением. Добавьте в **действующий** Caddyfile отдельный блок:

```caddyfile
share.nikitalebe.dev {
    reverse_proxy textdrop-share:8765
}
```

Основной домен и другие блоки не меняйте. Если блок поддомена уже существует, отредактируйте его, не дублируйте. Для стандартного пути внутри контейнера проверьте и примените конфигурацию (контейнер `caddy-caddy-1`):

```bash
docker exec caddy-caddy-1 caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker exec caddy-caddy-1 caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
curl -i https://share.nikitalebe.dev/api/session
```

DNS-запись `share` (A и, при наличии IPv6, AAAA) должна указывать на сервер. Caddy автоматически получает TLS-сертификат при доступных портах 80/443. Ожидаемый ответ проверки: HTTP 200 и `{"authenticated": false}`. Войдите с логином `admin` и паролем, заданным при установке. Другие учётки создаёт владелец в настройках.

Логи: `docker compose logs --tail=100 textdrop`. Обновление: `docker compose up -d --build`. Не выполняйте `docker compose down -v`, если хотите сохранить записи.

## Проверка и разработка

```bash
python3 -m unittest discover -s tests -v
node --check static/app.js
```

Для запуска без Docker установите зависимости из `requirements.txt` в виртуальное окружение (`python3 -m venv .venv`, `.venv/bin/python -m pip install --only-binary=:all: -r requirements.txt`). Затем задайте `TEXTDROP_PASSWORD` (12+ символов), `TEXTDROP_SECRET` (32+ символов), `TEXTDROP_SECURE=0` и выполните `.venv/bin/python server.py`. По умолчанию сервер слушает `127.0.0.1:8765`. Для HTTP-разработки используйте отдельный пароль. Файлы `deploy/textdrop.service` и `deploy/setup-env.py` оставлены как альтернативный запуск через systemd, без Docker.

## Данные и секреты

Docker: база `/data/notes.sqlite3` в томе `textdrop_data`; секреты в `.secrets/`, исключённом из Git и Docker build context. Без Docker: `data/notes.sqlite3` и `.env`. Файлы секретов доступны контейнеру для чтения; родительский каталог `.secrets` на хосте имеет права 0700.

Пароль меняется через кнопку учётной записи в шапке; активные сессии пользователя завершаются. `TEXTDROP_PASSWORD` задаёт пароль `admin` только при первом создании реестра; изменение секрета после установки не сбрасывает пароль учётки. Для бэкапа остановите приложение перед копированием базы либо используйте SQLite backup API. Удалённые сообщения хранятся в корзине 30 дней; окончательное удаление вручную требует подтверждения. Лимит записи — 100 000 символов. Лента загружается порциями по 50 записей; обновляется каждые 3 секунды в открытой вкладке.

## Резервная копия

План развития и готовность этапов: [ROADMAP.md](ROADMAP.md).

После обновления кода пересоберите контейнер, чтобы в него попала утилита `backup.py`:

```bash
sudo docker compose up -d --build
sudo sh deploy/backup.sh
```

Скрипт создаёт проверенную копию в `backups/` с уникальным именем. Приложение продолжает работать: используется SQLite backup API. После передачи дополнительно проверяется целостность каждой базы. С учётками копия — архив `.tar.gz`: `accounts.sqlite3`, `notes.sqlite3` владельца и базы `users/{id}/notes.sqlite3`. Каждая база сохраняется согласованным снимком; это не общая транзакция между пользователями. Реестр копируется первым; сессии из копии удаляются. Старый контейнер отдаёт прежний `.sqlite3`; скрипт принимает оба формата. Ошибка выгрузки удаляет незавершённый файл. Копии исключены из Git; каталог доступен только владельцу. При запуске через sudo копия принадлежит root.

Копия на том же диске не защищает от потери сервера. Храните дополнительную копию вне сервера. Автоматическое расписание, ротация и внешнее хранилище пока не настроены.

Для проверки восстановления, не затрагивая рабочие данные, скопируйте бэкап в отдельный каталог и запустите **отдельный** экземпляр приложения с `TEXTDROP_DATA`, указывающим на этот каталог, и другим портом. Для старого `.sqlite3` файл должен называться `notes.sqlite3`. Новый `.tar.gz` распакуйте с сохранением структуры в пустой каталог. Используйте отдельный секрет сессий; пароли учёток сохраняются в реестре, тестовый `TEXTDROP_PASSWORD` их не заменяет. Не направляйте тестовый экземпляр на рабочий том.

Для восстановления рабочей базы сначала остановите приложение и сохраните копию текущего тома. Восстанавливайте весь комплект баз только при остановленном сервисе; права файла должны позволять UID 10001 читать и записывать его. Не оставляйте WAL/SHM от другой базы рядом с восстановленной. После запуска проверьте вход и записи с двух устройств. Тесты восстановления на отдельной базе входят в `tests/test_backup.py`; восстановление рабочей базы автоматически не выполняется.

## Интерфейс чата

История расположена над полем ввода, новые сообщения появляются внизу. Когда вы читаете старую переписку, позиция сохраняется; кнопка «К новым сообщениям» возвращает вниз. Enter добавляет строку, Ctrl/Cmd+Enter отправляет. Светлая и тёмная темы переключаются в шапке; выбор сохраняется только на текущем устройстве, до ручного выбора используется системная тема.

Проверка темы: `node --test tests/theme.test.cjs`. Дополнительная браузерная проверка: `tests/chat.browser.cjs` (Node 22+, Playwright и Chromium, тестовый API, рабочая база не используется). Скриншоты сохраняются во временный каталог `textdrop-chat-captures`.

## Повторы отправки и черновики

Новый клиент передаёт `request_id` вместе с текстом. Повтор того же запроса возвращает прежнее сообщение, включая его id и дату; параллельные запросы обрабатываются атомарно. Тот же ключ с другим текстом получает HTTP 409. Повтор удалённого сообщения получает HTTP 410 и не восстанавливает его. Идентификаторы и хеши текста хранятся в дополнительной таблице `send_requests`, создаваемой автоматически; существующие записи сохраняются. Старые клиенты без ключа продолжают работать, но не получают защиту повторов. Намеренная повторная отправка одинакового текста использует новый ключ.

Черновик и ключ незавершённой отправки сохраняются в `localStorage` текущего браузера (ключ `textdrop-draft-v1`), а не синхронизируются между устройствами. Срок — 7 дней с последнего сохранения; устаревший черновик удаляется при следующем чтении. При истечении сессии текст остаётся и возвращается после входа. Успешная отправка очищает отправленный текст, но сохраняет то, что вы успели набрать во время запроса. Явный выход очищает локальный черновик. Если браузер запрещает хранение или закончилась квота, показывается предупреждение, текст остаётся в открытой вкладке. При очистке данных браузера локальные черновики теряются.

Регрессионные проверки: `node --test tests/*.test.cjs`, `tests/reliability.browser.cjs` (Node 22+, Playwright/Chromium, временный сервер и SQLite, без доступа к рабочей базе).

## Сбои и восстановление связи

При временной ошибке базы, сервера или сети последняя загруженная история остаётся на экране; черновик не очищается. Статус различает отсутствие соединения, недоступный сервер и таймаут. После успешного опроса синхронизация возобновляется и сообщение об ошибке загрузки исчезает. Можно нажать «Повторить подключение»; при сбое первоначальной загрузки такая кнопка есть и на экране входа.

При истечении сессии приложение предлагает войти заново, сохраняя черновик. Обычное обновление/перезапуск с прежним секретом сессий не требует повторного входа. Ошибки прокси с HTML вместо JSON не выводятся как технические ошибки парсинга; некорректный ответ не заменяет текущую историю. Ошибка отправки остаётся видимой до следующего действия, чтобы фоновый опрос не создавал впечатление успешной отправки.

## Редактирование сообщений

Нажмите «Изменить» под сообщением. Правки вводятся на месте; «Сохранить» или Ctrl/Cmd+Enter применяют их, «Отмена» или Esc закрывают редактор. Первоначальная дата и позиция сообщения не меняются, рядом со временем появляется «изменено». Черновик нового сообщения независим от редактора.

На сервере `PATCH /api/notes/{id}` принимает `text` и ожидаемую `version`. Версии и время изменения хранятся в отдельной таблице `note_versions`, создаваемой автоматически; исходная таблица сообщений совместима с предыдущим приложением. Проверка версии и запись выполняются одной транзакцией. При конфликте сервер возвращает HTTP 409 с актуальным сообщением в `current`; удалённая запись получает HTTP 410 и не создаётся заново. Повтор уже применённой правки с тем же текстом и предыдущей версией подтверждает результат без увеличения версии.

Когда другое устройство изменило запись, редактор показывает текущий серверный текст рядом с вашим вариантом. «Принять эту версию» закрывает редактор без записи, «Сохранить мой вариант» явно применяет ваш текст с повторной проверкой версии. Если за это время появится ещё одна правка, конфликт будет показан снова. Пустой текст не сохраняется.

Несохранённые правки сохраняются в памяти вкладки во время опроса, сетевой ошибки и повторного входа. Они не записываются в постоянный черновик: перезагрузка страницы, закрытие вкладки, явная отмена и выход закрывают редактор. При удалении записи на другом устройстве локальный вариант остаётся доступен для копирования до отмены.

Проверки двух устройств, конфликтов, повтора после потери ответа, фокуса и мобильных тем: `tests/edit.browser.cjs` (Node 22+, Playwright/Chromium, временная база).

## Корзина и ссылки

Кнопка «Удалить» переносит сообщение в корзину после подтверждения. Откройте раздел «Корзина», чтобы восстановить его с тем же ID и исходной датой. Для каждой записи показан срок хранения. Повтор удаления не продлевает 30 дней, повтор восстановления не создаёт дубль. «Удалить навсегда» требует отдельного подтверждения и удаляет только запись из корзины, не активное сообщение. Записи, удалённые до появления корзины, восстановить этим способом нельзя.

Восстановление увеличивает версию записи, чтобы открытый на другом устройстве старый редактор не перезаписал её незаметно. Черновик нового сообщения сохраняется при переходе между разделами. Редактирование в корзине недоступно; сначала восстановите запись. Закрепления сообщений в продукте не будет.

API: `GET /api/trash`, `POST /api/trash/{id}/restore`, `DELETE /api/trash/{id}`. Все операции требуют входа, изменения защищены от межсайтовых запросов. Архив хранится в отдельной таблице `trash`, поэтому предыдущая версия приложения при откате не покажет удалённые записи как активные. После истечения срока API запрещает восстановление; очистка удаляет просроченные записи при открытии корзины и фоновым проходом раз в час (при ошибке повторяет через минуту). SQLite-бэкап включает корзину.

HTTP/HTTPS-ссылки открываются в отдельной вкладке без доступа к исходной странице и без Referer. Пунктуация и переносы сохраняются, HTML остаётся текстом. Протоколы `javascript:`, `data:`, `ftp:` и адреса с логином/паролем не превращаются в ссылки. Адреса без `http://` или `https://` остаются обычным текстом. Превью и запросов к внешним сайтам при отображении сообщения нет.

Проверки восстановления, окончательного удаления, истечения срока, двух устройств и ссылок: `tests/trash-links.browser.cjs` (временный сервер и база, Node 22+, Playwright/Chromium).

## Компактный интерфейс

На телефоне и компьютере разделы, счётчик, статус и кнопка поиска занимают одну строку. Поле поиска открывается по нажатию; закрытие или Esc сбрасывают фильтр. Активный поиск остаётся видимым при смене ширины окна. Действия сообщения представлены иконками с доступными названиями и подсказками на всех устройствах. Полный статус соединения доступен в подсказке; ошибки также показываются текстом.

Регрессия плотности истории, поиска, действий, поворота экрана и короткого окна: `tests/mobile.browser.cjs` (Node 22+, Playwright/Chromium, тестовые данные).

## Длинные сообщения

В чате и корзине текст длиннее шести видимых строк сворачивается. «Развернуть» показывает сообщение целиком; кнопка «Свернуть» остаётся доступна при прокрутке. Превью пересчитывается при изменении ширины окна. Выбранное раскрытие сохраняется в текущей вкладке при синхронизации и переходе между разделами, а перезагрузка сбрасывает его.

Копирование и редактор используют полный исходный текст. Поиск проверяет всё сообщение и показывает найденное целиком; после закрытия поиска возвращается выбранное раскрытие. Целые ссылки в превью работают, обрезанный адрес становится обычным текстом до раскрытия.

Проверки шести строк, поиска по скрытому фрагменту, полного копирования и редактирования, синхронизации, корзины и экранов 320/390/1280px: `tests/collapse.browser.cjs` (Node, Playwright/Chromium, тестовые данные).

## Большая история и поиск

Чат открывает последние 50 сообщений. При прокрутке вверх подгружаются предыдущие; также доступна кнопка «Загрузить предыдущие». Позиция читаемого сообщения сохраняется. В корзине старые записи подгружаются вниз. Очень длинные сообщения могут уменьшить число записей на странице: объём JSON-ответа ограничен примерно 1 МБ.

Поиск выполняется на сервере по всей истории после паузы ввода 250 мс, включая ещё не загруженные записи. Это поиск подстроки без учёта регистра Unicode; `%` и `_` остаются обычными символами. Длина запроса — до 256 символов. Счётчик в поиске показывает число совпадений, в обычной ленте — общее число записей; подсказка содержит полные счётчики. Ошибка подгрузки сохраняет уже открытые сообщения и допускает повтор.

Опрос раз в 3 секунды получает только изменения после сохранённой версии: новые сообщения, правки, удаления и восстановления. Загруженные страницы остаются на месте, открытый редактор сохраняет введённый текст и позицию курсора. Для личного чата этого достаточно; SSE пока не требуется.

API после входа: `GET /api/notes/page?limit=50&q=...&before=...`, `GET /api/notes/changes?since=...&q=...`; аналогичные пути доступны для `trash`. Страница возвращает `items`, непрозрачный курсор `next`, `revision`, `total`, `matched`; изменения — `items` с признаком `matches`, `removed`, `revision`, `has_more` и счётчики. Курсор задаёт границу `(дата, id)`, поэтому удаление граничного сообщения не нарушает следующие страницы. Максимальный `limit` — 100. Старые GET-маршруты со списками сохранены для уже открытых старых клиентов; новый интерфейс ими не пользуется.

Миграция автоматически добавляет индексы и таблицы `sync_state`/`note_changes`. Журнал содержит только последнюю версию изменения для каждого id, без копии текста. Триггеры отслеживают также записи прежнего приложения при откате образа. Исходные таблицы не меняются, штатный бэкап перед деплоем остаётся включён. Поисковые запросы не записываются в HTTP-логи.

Проверки: `python3 -m unittest discover -s tests -v`, `tests/pagination.browser.cjs` (Node, Playwright/Chromium, временная база из 10 000 записей). Проверяются ограниченная первая загрузка, поиск старых записей, равные даты, удалённый курсор, сохранение позиции, два устройства, гонки запросов, редактор, сбой/повтор и мобильная верстка.

## Работа с файлами

Нажмите скрепку рядом с вводом, выберите один файл и отправьте его с подписью или без неё. В сообщении показаны имя и размер; нажатие скачивает файл. Подпись можно редактировать и очищать. Поиск находит имена файлов и подписи, содержимое файлов не индексируется. Для подходящих JPEG/PNG/WebP/GIF показаны миниатюры; нажатие открывает просмотр с отдельной ссылкой на оригинал.

При загрузке видны прогресс и отмена. После сетевой ошибки файл остаётся выбранным для повторной отправки; повтор не создаёт дубликат, даже если сервер уже сохранил файл до обрыва ответа. Выбранный файл хранится только в памяти вкладки: после перезагрузки его нужно выбрать заново. Идентификатор незавершённой отправки сохраняется вместе с именем, размером и подписью на срок черновика; повторный выбор того же файла использует прежний идентификатор, а содержимое дополнительно проверяет сервер. Байты файла в браузерное хранилище не записываются. Текстовый черновик сохраняется как раньше. Уже отправленные файлы доступны со всех устройств после входа.

По умолчанию допускается **125 МиБ на файл** и **3 ГиБ содержимого файлов суммарно**, включая миниатюры и корзину. В Docker параметры `TEXTDROP_FILE_LIMIT` и `TEXTDROP_STORAGE_LIMIT` задаются в байтах через окружение Compose; значения по умолчанию записаны в `compose.yaml`. Сервер проверяет квоту внутри транзакции, включая одновременные загрузки. Допускаются не более двух приёмов файлов одновременно; отмена и прерванные загрузки не оставляют записей. Таймаут браузера — 10 минут, ожидание очередного фрагмента на сервере — до 120 секунд.

Удаление перемещает сообщение вместе с файлом в корзину на 30 дней. До окончательного удаления файл можно скачать и восстановить с исходной датой. Окончательное удаление и истечение срока освобождают квоту. Физический файл SQLite может сохранять размер и повторно использовать освободившиеся страницы; служебные файлы базы и бэкапы не входят в квоту содержимого.

Байты и метаданные хранятся в дополнительной таблице `attachments` в той же базе, что и сообщения. Существующий SQLite backup автоматически включает файлы согласованной копией; отдельный каталог вложений для восстановления не нужен. Временные загрузки используют записываемый том `/data`, постоянные данные переживают пересоздание контейнера. Режим WAL позволяет отправлять сообщения во время скачивания. Для работы с BLOB требуется Python 3.11+; Docker использует Python 3.12.

Все файловые API требуют входа. Скачать файл можно через `GET /api/files/{id}`; ответ имеет тип `application/octet-stream`, `Content-Disposition: attachment`, `nosniff` и запрет активного содержимого. Исходные имена не используются как пути, управляющие символы убираются. `GET /api/storage` возвращает лимиты и занятый объём. Для `POST /api/files` тело состоит из UTF-8 JSON (`name`, `text`, `request_id`) и затем исходных байтов файла; заголовок `X-Textdrop-Metadata-Length` задаёт длину JSON в байтах. В ленте возвращается только `file: {name, size, sha256}`, без бинарного содержимого. Повторы отслеживаются в `file_requests`.

Проверки: `python3 -m unittest discover -s tests -v`, `tests/files.browser.cjs` (Playwright/Chromium, временная база, два устройства). Покрыты совпадение скачанных байтов, пустой файл, подпись, лимиты, обрыв/повтор, отмена, корзина, поиск, повторный вход и восстановление файла из бэкапа.

## Превью фотографий

Изображения определяются по содержимому, включая файлы без привычного расширения. Поддерживаются JPEG, PNG, WebP и первый кадр GIF. В ленте загружаются только миниатюры: максимум 640 пикселей по длинной стороне и 100 КиБ. Нативные `loading="lazy"` и `decoding="async"` откладывают загрузку и декодирование; фиксированная область с `object-fit: contain` сохраняет место и пропорции. Галерейных библиотек в браузере нет.

Нажатие увеличивает миниатюру в стандартном диалоге браузера. Оригинал скачивается по отдельной ссылке и сохраняется без изменений. Esc и кнопка закрытия возвращают фокус в историю. При завершении сессии открытый просмотр и его адрес очищаются.

Миниатюра создаётся по первому запросу и сохраняется в `attachment_images` в SQLite. Повторные запросы используют готовый JPEG; `ETag` и приватное кеширование с обязательной проверкой входа позволяют вернуть 304. Превью доступны и для ранее отправленных файлов. Они входят в существующий бэкап и квоту, сохраняются в корзине и удаляются вместе с оригиналом окончательно или по сроку. При заполненной квоте доступно скачивание без создания нового превью. Отказ по нехватке места запоминается на 60 секунд; повторная попытка возможна раньше при изменении занятого объёма или лимита. Временный кэш ограничен 256 записями.

Обрабатывается одно изображение за раз. Отдельный `preview.py` ограничен 256 МиБ адресного пространства, 5 секундами CPU и 8 секундами ожидания родительского процесса. Для обработки допускаются исходники до 32 МиБ и 24 мегапикселей; большие изображения, HEIC, SVG и повреждённые файлы остаются обычными скачиваемыми вложениями. Их лимит загрузки по-прежнему 125 МиБ. Ошибка декодирования кешируется, чтобы не расходовать CPU на каждом показе. Обработка исправляет EXIF-поворот и удаляет метаданные из миниатюры; оригинал не меняется.

На синтетических снимках 12 Мп измерены: JPEG 5,97 МБ → 46,8 КБ за 0,18 с (пиковый RSS обработчика около 33 МиБ), PNG 30,1 МБ → 46,7 КБ за 0,32 с (около 75 МиБ). Это локальные замеры, результаты зависят от фотографии и сервера. Закреплённая версия Pillow устанавливается только на сервере; в проверенном Linux-окружении она заняла около 20,5 МиБ на диске.

Проверки: после установки зависимостей `python3 -m unittest discover -s tests -v`; `tests/previews.browser.cjs` использует временную базу и синтетические картинки. Проверяются форматы, размеры, EXIF, ограничение ресурсов, один запуск при параллельных запросах, кэш/квота/бэкап, авторизация, отсутствие фоновых загрузок оригинала, мобильная компоновка и отказ превью без потери доступа к файлу.

## Исправления по результатам аудита

Завершение отправки привязано к сессии: ответ, пришедший после выхода и повторного входа, не очищает новый черновик и не меняет состояние новой отправки. Файловые повторы защищены также после перезагрузки и повторного выбора файла; явный выход очищает сохранённый идентификатор.

Авторизация записывающих API (кроме входа) проверяется до чтения тела. На чтение JSON выделяется 10 секунд суммарно, включая медленную подачу фрагментов; превышение возвращает 408. Ограничены ожидание заголовков и число обслуживающих HTTP-потоков (64); файловая загрузка сохраняет собственные ограничения.

Регрессии: `tests/audit.browser.cjs`, `tests/test_audit.py` и `tests/draft.test.cjs`. Проверки выполняются на временных данных.

## Учётные записи

Открытой регистрации нет. Владелец входит как `admin` с прежним паролем: существующие записи, корзина и файлы остаются его данными. После первого обновления потребуется войти снова — старые сессии недействительны.

Нажмите кнопку учётной записи в шапке → «Пользователи». Укажите логин (3–32 латинские буквы, цифры, `.`, `-`, `_`) и пароль от 12 символов. До 50 учёток на сервис. Каждый пользователь получает собственный чат, поиск, корзину, файлы и черновик браузера. Совместных чатов нет. Владелец управляет доступом, но его интерфейс не показывает чужое содержимое.

Владелец может отключать/включать пользователей и задавать новый пароль. Отключение и смена пароля отзывают все сессии пользователя. Любой пользователь может сменить свой пароль, подтвердив текущий. Выход отзывает текущую сессию. Владелец не может отключить себя. Удаления учёток пока нет: отключение сохраняет историю.

Лимит **3 ГиБ общий** для файлов и миниатюр всех пользователей, включая корзины отключённых учёток. Максимум одного файла — **125 МиБ**. Переполнение требует очистить корзину пользователя с файлами либо изменить лимит на сервере. Служебные базы и бэкапы в квоту не входят.

Реестр `/data/accounts.sqlite3` содержит соль и хеши PBKDF2-SHA256 (600 000 итераций), роли и хеши отзываемых сессий. Контент новых пользователей — `/data/users/{случайный id}/notes.sqlite3`; логин не используется в путях. HTTP API выбирает хранилище по сессии. JSON-запросы интерфейса передают `X-Textdrop-User`, чтобы смена cookie в другой вкладке не отправила чужой черновик. Для стороннего клиента: сначала `GET /api/session`, затем передавайте `user.id` в этом заголовке; нативные скачивания и превью используют cookie без обязательного заголовка.

Сохраняйте реестр вместе со всеми базами. Откат на версию до учёток допустим только как аварийное временное действие: она обслуживает прежнюю базу владельца и использует установочный пароль, новые учётки в ней недоступны. При недоступном пароле владельца восстановите проверенную копию реестра либо выполните локальный сброс через `Accounts.change_password('owner', ...)` при остановленном приложении; пароль вводите через `getpass`, не аргумент командной строки. Файлы секретов и реестр не удаляйте.

Проверки: `tests/test_accounts.py`, `tests/test_account_backup.py`, `tests/accounts.browser.cjs` — миграция, изоляция и запреты чужих операций, отзыв сессий, общая квота при параллельной загрузке, восстановление всех баз и сценарий двух пользователей на телефоне/компьютере.
