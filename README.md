# Textdrop

Личная лента для обмена текстом между устройствами: один пароль, SQLite, поиск, копирование и удаление. Python 3.12+, без сторонних библиотек. Адрес: `https://share.nikitalebe.dev`.

## Запуск с существующим Caddy в Docker

Выполняйте команды в обычной SSH-сессии с доступом к Docker. Нужен Docker Compose v2+. Текущий контейнер Caddy — `caddy-caddy-1`, сеть — `caddy_default`. Проверить их можно так:

```bash
docker ps --format 'table {{.Names}}\t{{.Networks}}'
docker network inspect caddy_default --format '{{.Driver}}'
```

Используйте пользовательскую bridge-сеть Caddy, поддерживающую DNS контейнеров. Если Caddy использует `host` или стандартную сеть `bridge`, потребуется отдельная общая сеть и её подключение в конфигурации Compose Caddy.

```bash
cd ~/textdrop
python3 deploy/setup-docker-secrets.py
python3 deploy/setup-docker-secrets.py --check
docker compose up -d --build
docker compose ps
```

По умолчанию используется сеть `caddy_default`; для другой сети задайте `CADDY_NETWORK`. Скрипт спрашивает пароль интерактивно и не перезаписывает секреты. Повторный запуск создаёт только недостающие файлы, в том числе после прерванной настройки. Проверка `--check` не создаёт и не меняет секреты. Приложение работает без root, хранит SQLite в именованном томе и не публикует порт 8765 на хосте. Caddy обращается к нему по имени `textdrop-share` в общей сети.

Чтобы найти действующий Caddyfile на хосте, посмотрите bind mounts:

```bash
docker inspect caddy-caddy-1 --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
```

Если `/etc/caddy` смонтирован как каталог, файл находится в его источнике под именем `Caddyfile`. Сделайте резервную копию файла перед изменением. Добавьте в **действующий** Caddyfile отдельный блок:

```caddyfile
share.nikitalebe.dev {
    reverse_proxy textdrop-share:8765
}
```

Основной домен и другие блоки не меняйте. Если блок поддомена уже существует, отредактируйте его, не дублируйте. Для стандартного пути внутри контейнера проверьте и примените конфигурацию (контейнер `caddy-caddy-1`):

```bash
docker exec caddy-caddy-1 caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker exec caddy-caddy-1 caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
curl -i https://share.nikitalebe.dev/api/session
```

DNS-запись `share` (A и, при наличии IPv6, AAAA) должна указывать на сервер. Caddy автоматически получает TLS-сертификат при доступных портах 80/443. Ожидаемый ответ проверки: HTTP 200 и `{"authenticated": false}`. Откройте адрес на каждом устройстве и введите одинаковый пароль.

Логи: `docker compose logs --tail=100 textdrop`. Обновление: `docker compose up -d --build`. Не выполняйте `docker compose down -v`, если хотите сохранить записи.

## Проверка и разработка

```bash
python3 -m unittest discover -s tests -v
node --check static/app.js
```

Для запуска без Docker задайте `TEXTDROP_PASSWORD` (12+ символов), `TEXTDROP_SECRET` (32+ символов), `TEXTDROP_SECURE=0` и выполните `python3 server.py`. По умолчанию сервер слушает `127.0.0.1:8765`. Для HTTP-разработки используйте отдельный пароль. Файлы `deploy/textdrop.service` и `deploy/setup-env.py` оставлены как альтернативный запуск через systemd, без Docker.

## Данные и секреты

Docker: база `/data/notes.sqlite3` в томе `textdrop_data`; секреты в `.secrets/`, исключённом из Git и Docker build context. Без Docker: `data/notes.sqlite3` и `.env`. Файлы секретов доступны контейнеру для чтения; родительский каталог `.secrets` на хосте имеет права 0700.

Смена пароля требует смены секрета сессий и пересоздания контейнера. Для бэкапа остановите приложение перед копированием базы либо используйте SQLite backup API. Удаление записей окончательное. Лимит записи — 100 000 символов. Лента загружается целиком и рассчитана на личное использование; обновляется каждые 3 секунды в открытой вкладке.

## Резервная копия

План развития и готовность этапов: [ROADMAP.md](ROADMAP.md).

После обновления кода пересоберите контейнер, чтобы в него попала утилита `backup.py`:

```bash
sudo docker compose up -d --build
sudo sh deploy/backup.sh
```

Скрипт создаёт проверенную копию в `backups/` с уникальным именем. Приложение продолжает работать: используется SQLite backup API. После передачи файла дополнительно проверяются целостность и наличие таблицы записей. Ошибка выгрузки удаляет незавершённый файл. Копии исключены из Git; каталог доступен только владельцу. При запуске через sudo копия принадлежит root.

Копия на том же диске не защищает от потери сервера. Храните дополнительную копию вне сервера. Автоматическое расписание, ротация и внешнее хранилище пока не настроены.

Для проверки восстановления, не затрагивая рабочие данные, скопируйте бэкап в отдельный каталог и запустите **отдельный** экземпляр приложения с `TEXTDROP_DATA`, указывающим на этот каталог, и другим портом. Файл должен называться `notes.sqlite3`. Проверяйте записи с отдельным секретом сессий и тестовым паролем. Не направляйте тестовый экземпляр на рабочий том.

Для восстановления рабочей базы сначала остановите приложение и сохраните копию текущего тома. Заменяйте базу только при остановленном сервисе; права файла должны позволять UID 10001 читать и записывать его. Не оставляйте WAL/SHM от другой базы рядом с восстановленной. После запуска проверьте вход и записи с двух устройств. Тесты восстановления на отдельной базе входят в `tests/test_backup.py`; восстановление рабочей базы автоматически не выполняется.

## Интерфейс чата

История расположена над полем ввода, новые сообщения появляются внизу. Когда вы читаете старую переписку, позиция сохраняется; кнопка «К новым сообщениям» возвращает вниз. Enter добавляет строку, Ctrl/Cmd+Enter отправляет. Светлая и тёмная темы переключаются в шапке; выбор сохраняется только на текущем устройстве, до ручного выбора используется системная тема.

Проверка темы: `node --test tests/theme.test.cjs`. Дополнительная браузерная проверка: `tests/chat.browser.cjs` (Node 22+, Playwright и Chromium, тестовый API, рабочая база не используется). Скриншоты сохраняются во временный каталог `textdrop-chat-captures`.

## Повторы отправки и черновики

Новый клиент передаёт `request_id` вместе с текстом. Повтор того же запроса возвращает прежнее сообщение, включая его id и дату; параллельные запросы обрабатываются атомарно. Тот же ключ с другим текстом получает HTTP 409. Повтор удалённого сообщения получает HTTP 410 и не восстанавливает его. Идентификаторы и хеши текста хранятся в дополнительной таблице `send_requests`, создаваемой автоматически; существующие записи сохраняются. Старые клиенты без ключа продолжают работать, но не получают защиту повторов. Намеренная повторная отправка одинакового текста использует новый ключ.

Черновик и ключ незавершённой отправки сохраняются в `localStorage` текущего браузера (ключ `textdrop-draft-v1`), а не синхронизируются между устройствами. Срок — 7 дней с последнего сохранения; устаревший черновик удаляется при следующем чтении. При истечении сессии текст остаётся и возвращается после входа. Успешная отправка очищает отправленный текст, но сохраняет то, что вы успели набрать во время запроса. Явный выход очищает локальный черновик. Если браузер запрещает хранение или закончилась квота, показывается предупреждение, текст остаётся в открытой вкладке. При очистке данных браузера локальные черновики теряются.

Регрессионные проверки: `node --test tests/*.test.cjs`, `tests/reliability.browser.cjs` (Node 22+, Playwright/Chromium, временный сервер и SQLite, без доступа к рабочей базе).
